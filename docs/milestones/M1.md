## Part 1: The first version (owners: claudea; gates/routing: abraham)

**User, task and success check (claudea).** *Who:* an analyst on a sales team. Distributors email a sell-out file and a question, usually "how did our region do this quarter?". *Today* the analyst decodes each file by hand, since every distributor exports differently, looks the distributor up in the sales database, builds a chart and emails a report. *They want* the decoding and comparison done, the report saved and the email ready to read and send. *Done* is a saved report whose figures match the database for that distributor and quarter, plus one drafted email to that distributor's contact that states the revenue, points at the report and carries no one else's data.

**Core task and use cases.** The core task is the one the analyst does most: turn a distributor's quarterly file and question into a saved report, a chart and a drafted covering email, taken as far as it goes without waiting for the distributor's answer. It splits into six use cases: `standard_report` (a clean file in the known layout), `messy_file` (an unfamiliar export to decode first: semicolons, decimal commas, other headers, a column per month), `compare_check` (this quarter against the last before sending), `batch_reports` (the operator's request for several distributors at once), `status_question` (a question about work already done) and `out_of_scope` (a request for margins or other distributors' sales, declined). A case that needs the distributor's answer ends with a pending clarifying question, and the operator is told. The **success check** reads the sandbox rows stamped with the run's ID and recomputes revenue from `orders`; it never takes the agent's word for what it did.

**Test tasks (claudea; `tasks/`).** *How we chose them:* one working day's inbox, one task per use case, in the shapes we expect most (a clean CSV, a German-locale export), plus the two late-day operator requests (a comparison and a batch). Both paths are covered, three tasks run on the agent path, and `messy_file_semicolon` could be misrouted, since its message is word for word the clean task's. `tasks/dev/messy_file_tab` is kept for tuning prompts and never measured. Each check reads the environment, not the reply: the report and pending rows the run stamped, and the revenue recomputed from `orders`. Each has planted-success and no-effect tests (`tests/test_domain_checks.py`, `tests/test_checks.py`); other tests cover wrong figures, wrong recipients, duplicates, leaks and skipped work.

| Task | Use case, path | What it tests | Check (`checks/`) |
|---|---|---|---|
| `standard_report_clean` | standard_report, workflow | the clean file, end to end | `standard_report.py`: the report's `total_revenue` and `period` = the database's, one pending email to the contact stating that revenue for that report, no margin or other distributor, no duplicates |
| `messy_file_semicolon` | messy_file, agent; **could be misrouted**: its text is word for word the clean task's, only the file differs | decoding a semicolon/decimal-comma file with German headers | `messy_file.py`: as above, plus the report carries the file's 1,240 units (the task's `expect:`, which the agent never reads) |
| `compare_check_last_quarter` | compare_check, agent | Q3 against Q2 for Cedar (62,799.60 to 67,246.55: up) | `compare_check.py`: report carries both quarters' revenue; a reply that claims the wrong direction fails |
| `status_question_done_work` | status_question, workflow | a question about a report the seed saved and sent | `status_question.py`: a reply gives the reported revenue; the run writes nothing |
| `out_of_scope_margins` | out_of_scope, workflow | a request for margins and Acme's sales | `out_of_scope.py`: a pending reply to the contact; nothing written names another distributor or a margin |
| `batch_reports_two` | batch_reports, agent (planned) | two new requests at once | `batch_reports.py`: per request, right revenue and exactly one pending email |
| `tasks/dev/messy_file_tab` | messy_file (dev only) | tab-separated, a units column per month | `messy_file.py` |

**The sandbox (claudea).** One SQLite file in the run's state folder (`sandbox/db.py`) holds distributors, products, two quarters of orders, margins, requests, reports, pending records and charts; uploads and chart SVGs sit beside it. In `sandbox/seed.py`, `reset()` empties it, `seed(task)` loads the base data, the task's input and its stranger's message on the channel, and `seed(None)` loads the demo data `make app` serves. "Now" is fixed (`db.NOW = 2026-10-05`), so every run repeats. Every write is stamped (`sandbox/stamp.py`) with the run's ID, the console session's ID, or `manual` for a write made by hand. The pages and the tools share these modules. Only `sandbox/margins.py` reads margins, and `tests/test_domain_sandbox.py` fails if `agent/`, `checks/` or a tool's module imports it.

**Console, product page and workflows (console agent side: abraham; the rest: claudea).** The console and the runner both call `agent.service.operator_turn`. The console (`/console`) is the analyst's chat: it shows each reply and its actions, and under it the named request's saved figures, chart and drafts with **Send** and **Discard**. A message naming work to do is a new task; a question about what was done is answered from the saved records, with no writes. The product page (`app/product.py`, no agent; `tests/test_product.py`): `/` lists the requests and the drafts waiting to be sent; `/requests/<id>` shows the file, thread, reports, charts and pending records with Send and Discard, and a form to **email a report by hand**, the core task without the agent (body prefilled from the database, recipient always the request's contact, stamped `manual`); `/query` shows any distributor's quarter with a chart and the change from the last. `standard_report` (`agent/workflows.py`) runs six fixed steps (parse, query, chart, save, draft through the critique, `draft_report_email`) and ends `unknown_layout` on an unknown header, so a misrouted messy file shows instead of passing silently. `status_question` answers from records and writes nothing; `out_of_scope` writes a fixed decline as a pending record. [Workflow details](M1-evidence.md).

**Four gates.** The [handout](https://canvas.uchicago.edu/courses/75218/assignments/921328), Part 1 task 5, and Lecture 1 slides 33–36 motivate the boundary:

| Gate | `messy_file` | `standard_report` | Evidence / verdict-changing result |
|---|---|---|---|
| 1. Do the steps vary? | Pass for unfamiliar layouts: an observed parse can require another delimiter, decimal convention, or clarification before continuing | Fail: the known header permits a fixed parse/query/chart/save/draft sequence | `messy_file_semicolon` and the tab-separated development fixture expose different layouts. These two formats alone could be branches; if real inputs reduce to a stable branch list, use a workflow. A1's 19 distinct sequences in 60 agent runs, with the top three covering 37/60, warns against assuming every variation needs an agent |
| 2. Can damage be limited? | Pass: tools bind one selected request/distributor, exclude margins, and cannot send; calls/tokens/time are bounded | Pass: the workflow uses those same scoped tools | Request-scope and foreign-report tests; narrowing reach and replacing send with a pending draft are the design limits that make the agent case acceptable |
| 3. Will an error be caught in time? | Pass with review: scoped sales and saved records support checks; the operator reviews the pending email before the irreversible send | Pass with the same review requirement | A wrong report can be replaced by a new version; an unsent draft can be left unsent. Neither a tool trace nor syntactically valid parsing proves correctness. The external critique and independent task checks help detect errors; a person remains before send |
| 4. Is the added cost justified? | Pass under the explicit domain estimate `f=0.10` and correction-cost assumption below; this is a design estimate awaiting live evidence | Fail at estimated `f=0`: no extra correct cases are expected for the known sequence | The calculation below gives the break-even and sensitivity. Measured zero benefit reverses the messy-file decision; unit tests do not estimate it |

A1 provides provisional cost evidence, not sales-agent performance: `65125727`, `gpt-4.1-mini`, 60 runs/arm. [Source, definitions and sensitivity](M1-evidence.md).

| A1 arm | Passes / runs | Mean cost per run | Median / p95 latency |
|---|---|---|---|
| Direct | 20/60 | $0.000436867 | 0.750 / 1.000 s |
| Workflow | 16/60 | $0.000595960 | 1.141 / 1.406 s |
| Agent | 15/60 | $0.001991660 | 4.953 / 5.687 s |

Its workflow cost `c=$0.000595960` and multiplier `m=3.34194` imply $0.001395700 incremental cost. Measured A1 benefit share is zero: no issue crosses from workflow below 5/10 to agent at least 5/10. For unfamiliar sales layouts we instead **assume** 10% incremental success, giving $0.013957 per extra success versus an **assumed** $10.69 correction cost (15 minutes, BLS wage proxy). Break-even is 0.01306%; known-layout benefit is estimated zero. A 10% routing share gives $0.000735530/run before routing overhead. These estimates require domain validation.

Routing selects scope from trusted records before applying switches. Only ambiguous work/status intent uses classification. Unknown/ambiguous selections require clarification; status follow-ups reuse previously resolved IDs. Header recognition does not validate every file row.

**Approval line.** Ranked from easiest to undo to hardest: reads (`parse_file`, `query_sales`) change nothing; a chart or a report is superseded by a new version; a pending email or question is discarded with one click and reaches no one; the operator's send to the distributor cannot be recalled. The line sits between the pending records and the send. Above it the system acts alone; below it is the send, whose text the model writes and which could carry private figures (Lecture 1, slide 37), so the operator sends it by hand from the product page (`channel.send(..., sender="operator")`). The decline's text is a fixed template, so it could sit above the line; we keep it below, because it answers exactly the requests that ask for private data, and one click costs the analyst little. The agent has no send tool; Milestone 2 enforces the line in code, and the approvals page stays empty until then. Part 3's table gives each action's grid place, what happens if it is wrong, and its undo path.

**Trifecta.** All three properties are present: untrusted input (distributors' messages and uploads on the channel), private data (the `margins` table and other distributors' orders, every record synthetic with `SYN-` IDs) and a way out (a send on the channel), the trifecta of Lecture 1, slide 49. Request-bound tools exclude margins and other distributors, and the agent cannot send, so the way out passes through a person. The critique adds limited detection, not a guarantee; the operator's review remains necessary. Delivery is a local simulation; a draft can also be downloaded as an `.eml` with its charts.

### The critique loop (claudea)

**Where it helps: `draft_report_email`.** Slide 43's three gates hold. *A check without solving the task:* the recipient, quarter and revenue are each a lookup or one SQL sum (`sales.distributor_sales`), with no report to redo. *The critic knows what the author did not:* it reads the stored contact and quarter, not the stranger's claim, and recomputes revenue from `orders`. Some authors already see these facts, so this gate holds only where a fact was withheld: the planner never sees the contact address (it writes `$fill`), so a drafting model can invent one. The baseline shows it: in all three `batch_reports_two` runs (`results/baseline/baseline-batch_reports_two-s0{1,2,3}-*.trace.jsonl`) the critique returned **6 drafts** addressed to a literal `$fill:request.contact_email`, `{$fill:request.contact_email}` or `client@example.com`; all 6 were revised, passed, and their runs passed their checks. *A limit and a log:* two rounds, each a `critique` event.

**The check** (`agent/critique.py`, `check(request_id, draft)`) is a pass or fail with a reason, from the sandbox alone, never a task's check: the recipient is the request's `contact_email`; `figures.period` is the request's; `figures.total_revenue`, and the previous quarter's and the change when a comparison is asked for, match the database within 0.01; a declared `file_total_units` matches the upload's units column; the body states the true total and no wrong revenue, quarter or direction (`sandbox/report_validation.py`); it leaves no unfilled placeholder such as `[Name]`, names no other distributor and mentions no margins. These are bounded pattern rules, not full understanding of the prose, and they do not certify every claim; the operator still reads the draft. **Bound:** `rounds=2` (`CRITIQUE_ROUNDS`, `agent/workflows.py`): check, one tool-free revision with the reason, check again. Each round logs its verdict (`pass`, `revise`, `held`), reason and changed fields. A draft still failing is **held**: no pending record is written, the run ends `critique_held`, and the operator is told. Switch `critique.report_email`: `off | external`. **Paths:** the `standard_report` workflow and both agent paths (through `EmailGate`) call the same `critique.run`. **Tests** (`tests/test_workflows.py`, fake models): a failing draft is revised with its reason and never written at the bound, and a passing draft is written once.

**Where it does not help: the `out_of_scope` decline** (fixed template, `agent/domain_workflows.py`). Code writes every word and fills its one fact from the request record, so a check would read the same record the template did: the critic knows nothing new, and slide 43's second gate fails. A model-written clarifying question has no critique either: no record can say whether it is the right question, so the first gate fails; the operator reads it before sending. This does not claim such a check is impossible, only that M1 has no reliable one.

**Assignment 2's result** (Myron's [agentic-ai-assignment2](https://github.com/MyronLiu999/agentic-ai-assignment2), commit `df425cc`, `reports/LAB_02.json`, `gpt-4.1-mini`, 18 runs per configuration, read 2026-10-31). With two rounds, self and external critique averaged 0.22 and 0.17 rounds per run and changed no draft, while success fell from 5/18 (off) to 3/18 and 2/18: its check tested facts the author already had right. It predicts a critique pays only where the author can be wrong about a fact the critic sees. Our baseline differs on exactly that: 6 drafts changed in 18 runs (21 rounds, 1.17 per run), none held. One miss remains (`baseline-messy_file_semicolon-s01-1799cc`): at the baseline's commit the critic did not check the file's unit total, which a later fix added for declared totals. [Source and test detail](M1-evidence.md).

### Write identity and environmental confirmation

Keys hash run ID, bound request ID, tool and logical step/effect fields; sorted JSON normalizes equivalent integral numbers. Chart identity uses ordered labels/values, not title; reports use kind/period; emails use recipient/report; questions use request/tool. Prose and model round do not change identity. Same-effect retries return the first artifact; genuine revisions require new logical keys. Database uniqueness prevents duplicate effects; operator sending first atomically claims a pending record.

| Write | Environment read that confirms it | If it cannot answer; escalation |
|---|---|---|
| Chart | `charts.get(chart_id)` plus SVG file read | Halt/hold; analyst inspects row and artifact before retry |
