## Part 1: The first version (owners: claudea; the gates and routing, abraham)

**User, task and success check** (owner: claudea). *Who:* an analyst on a sales team. Distributors email
a sell-out file and a question, usually "how did our region do this quarter?". *Today* the analyst decodes
each file by hand (every distributor exports differently; about half the time), looks the distributor up in
the sales database, builds a chart and emails a report. *They want* the decoding and comparison done, the
report saved and the email ready to read and send. *Done* is a saved report whose figures match the database
for that distributor and quarter, plus one drafted email to that distributor's contact that states the
revenue, points at the report and carries no one else's data.

The **core task** is that quarterly report, taken as far as it goes without a stranger's answer: a file that
cannot be decoded ends with a pending clarifying question, and the operator is told. Its **use cases**:
`standard_report` (a clean file in the known layout), `messy_file` (another layout: semicolons, decimal
commas, other headers, a column per month), `compare_check` (check against last quarter before sending),
`status_question` (a question about done work), `out_of_scope` (a request for margins or other
distributors' sales) and `batch_reports` (several requests at once). The **success check** reads the
sandbox rows stamped with the run's ID and recomputes revenue from `orders`; it never takes the agent's word.

**Test tasks** (owner: claudea; `tasks/`). *How we chose them:* one working day's inbox, one task per use
case, in the shapes we expect most (a clean CSV; a German-locale export) plus the two late-day operator
requests. `tasks/dev/messy_file_tab` is kept for tuning prompts.

| Task | Use case, path | What it tests | Check (`checks/`) |
|---|---|---|---|
| `standard_report_clean` | standard_report, workflow | the clean file, end to end | `standard_report.py`: the report's `total_revenue` and `period` = the database's, one pending email to the contact stating that revenue for that report, no margin or other distributor, no duplicates |
| `messy_file_semicolon` | messy_file, agent; **could be misrouted**: its text is word for word the clean task's, only the file differs | decoding a semicolon/decimal-comma file with German headers | `messy_file.py`: as above, plus the report carries the file's 1,240 units (the task's `expect:`, which the agent never reads) |
| `compare_check_last_quarter` | compare_check, agent | Q3 against Q2 for Cedar (62,799.60 to 67,246.55: up) | `compare_check.py`: report carries both quarters' revenue; a reply that claims the wrong direction fails |
| `status_question_done_work` | status_question, workflow | a question about a report the seed saved and sent | `status_question.py`: a reply gives the reported revenue; the run writes nothing |

`tests/test_checks.py`; other tests cover wrong figures, recipients, duplicates, leaks and skipped work.

**The sandbox and the three properties** (owner: claudea). One SQLite file in the run's state folder
(`sandbox/db.py`) holds distributors, products, two quarters of orders, margins, requests, reports, pending
records and charts; uploads and chart SVGs sit beside it. `sandbox/seed.py`: `reset()` empties it,
`seed(task)` loads base data, the task's input and its stranger's message on the channel, and `seed(None)`
loads the demo data `make app` serves. "Now" is fixed (`db.NOW = 2026-10-05`). Every write is stamped
(`sandbox/stamp.py`) with the run's ID, the console session's ID, or `manual`. Pages and tools share these
modules. The three properties are carried by:

- *Input it does not control:* the distributor's message (`channel/`) and every cell of the upload
  (`sandbox/files.py`).
- *Private data:* the `margins` table and other distributors' orders, all `SYN-`. Only `sandbox/margins.py`
  reads margins; `tests/test_domain_sandbox.py` fails if `agent/`, `checks/` or a tool's module imports it.
- *A way out:* the report email, sent by the operator from `/requests/<id>` onto the distributor's thread,
  where it cannot be recalled.

**Console, product page and workflows** (console: abraham; the rest: claudea). The console and the runner
both call `agent.service.operator_turn`; routing (below) tells a new task from a status question. The
product page (`app/product.py`, no agent; `tests/test_product.py`): `/` lists requests and pending records;
`/requests/<id>` shows the file, thread, reports, charts and pending records with **Send** and **Discard**
buttons, and a form to **email a report by hand** (the core task without the agent: body prefilled from the
database, recipient always the request's contact, stamped `manual`); `/query` shows a quarter with a chart and
the change from last quarter. `standard_report` (`agent/workflows.py`) runs six fixed steps (parse, query,
chart, save, draft through the critique, `draft_report_email`) and ends `unknown_layout` on an unknown header,
so a misrouted messy file shows. `status_question` answers from records and writes nothing; `out_of_scope`
writes a fixed decline as a pending record. [Workflow details](M1-evidence.md).

**Boundary: four gates (Abraham).** The actual
[Milestone 1 handout](https://canvas.uchicago.edu/courses/75218/assignments/921328),
Part 1 task 5, pp. 5–7, supplies these gates (Lecture 1, slides 33, 34, 36; read
2026-10-31). The design choice is agent for `messy_file`, workflow for `standard_report`.

|---|---|---|---|
| 1. Recomputed from that JSON: `m = agent mean cost / workflow mean cost = 3.34194` and
`c = $0.000595960`. The source defines `f` precisely as the fraction of six issues for which
workflow passes fewer than five of ten runs and agent passes at least five of ten. None qualify:
`f = 0/6 = 0`. This is not a per-run fallback probability. The report's analysis fields are null;
these values are explicitly derived from its cost and per-issue counts using the
[A1 format definitions](https://github.com/MyronLiu999/agentic-ai-assignment1/blob/65125727e233902e9d69ba9655e4fe1a6ec4c715/checks/FORMATS.md)
(read 2026-10-31).

**Gate 4 economics.** Using A1's provisional workflow cost c=$0.000595960 and multiplier m=3.34194 gives an incremental cost of $0.001395700 per case. With an assumed 10% incremental success rate for unfamiliar layouts, cost per extra correct case is $0.013957, below the assumed $10.69 correction cost (15 minutes at the [BLS wage proxy](https://www.bls.gov/ooh/math/operations-research-analysts.htm), read 2026-10-31). Break-even f is 0.01306%; both the domain success rate and correction time are assumptions, not project measurements. For known layouts f is estimated at zero, so no finite cost per additional success exists. At an illustrative 10% routing share, blended cost is $0.000735530/run, excluding routing overhead. [Calculations and sensitivity](M1-evidence.md) distinguish routing share from benefit share.

Routing applies the configured `control.<use_case>` switch after selecting scope from records.
Only ambiguous operator intent uses a model, offered no tools and no outside file contents;
request IDs and distributors remain code-selected. Unknown IDs, exclusions/alternatives, and
ambiguous multi-request commands require clarification. The standard fingerprint is a header
test, not a claim that all file rows are valid. Status questions can resolve an exact distributor
name/ID plus a quarter/year to one stored request; duplicate or unmatched references need clarification.
A recognized generic status follow-up reuses the last resolved route's IDs from that session
trace, including status-only selections; without that evidence it asks for a selection.

**Action table and approval line** (owner: claudea; tool columns: myron). The action table appears once,
as Part 3's tool table. A trace shows a call happened, not that it was right; checks and the operator's
review supply that. Ranked from easiest to undo: (1) the reads change nothing; (2) a chart or report can be
superseded by a new keyed version; (3) a drafted email or question is a pending record the operator can
leave unsent or **Discard**. **The line** falls here. Below it: (4) the operator's send on the outside channel,
which a distributor reads and no one can recall. Its text is model-written, and slide 37 puts a reply that
could leak private data under "do not automate", so a person sends it. The agent has no send tool and no
workflow sends; we have no fixed-template send to place above the line.

**Trifecta** (slide 49). Untrusted input: `channel/` and `sandbox/files.py`. Private data: `margins`
(`sandbox/margins.py`) and other distributors' `orders`. Way out: the pending email (`sandbox/pending.py`),
sent from `app/product.py`. We narrow each in code: `tools.build(request_id)` fixes the distributor from the
request record and no tool imports margins; a person stands before the way out; the critique fails a draft
naming another distributor or margins. The leg we cannot remove is the analyst's judgment at send; they see
the full text first, and the critique does not catch every disclosure.

### Plan design and step sizes (Abraham)

Planning suits batch work because each selected request has identifiable deliverables; validation checks scope, ordering, dependencies, observable outcomes and unused artifacts before execution. The reactive messy-file path instead chooses its next step from observations. A failed read checkpoint permits bounded replanning, preserving the completed prefix; an uncertain write halts. Code records plan versions, diffs and repeat diagnostics, but those records do not establish semantic correctness. The planner receives allowlisted IDs and contracts, not distributor text; request period and contact are resolved by code at runtime. Myron's prior A2 issue-triage experiment found 7/18 agent passes versus 5/18 planned with critique off, despite fewer tokens; this does not measure our project. [Source, detailed validation, bounds and A2 data](M1-evidence.md).

Bounds and their rationales are traced. Checks run around calls and before further tools. An
already-running synchronous operation can overshoot a time/token allowance; this is a
cooperative stop, not an interrupt. The router's optional classification call precedes the
execution budget. With planning off, a batch uses separate request loops, each with its own
execution limits while still subject to the shared session token ceiling.

Both paths use the same email gate. Saved report identity, figures and comparison requirement remain fixed during revision; planned recipients are bound to the trusted contact. A held draft produces no pending email.

### Does it know what it did? (Abraham)

This inventory describes code and scripted tests as of 2026-10-31, compared with
the live batch trace B:9–58 and messy-file trace
`traces/dev-myron-live-02-messy_file_semicolon-s01-f55d9b.trace.jsonl`: parsing,
queries, saved report and pending email are visible, but the missing file total
shows why recorded success is not semantic correctness. "Survives" means the record survives reopening the same run/session;
starting a fresh evaluation run deliberately resets its sandbox. Durable evidence does not
imply automatic execution resumption: neither executor reloads an interrupted tool conversation
or partially completed graph. A new work turn starts a new execution. Status follow-ups do
recover the selected IDs and read durable domain records.

| Path / step | Recorded status or evidence | Can the model read it? | Can code read it? | Survives restart? |
|---|---|---|---|---|
| Batch: select requests | `route` event with IDs, path, and provenance; inbox rows | Planner receives allowlisted record IDs/counts only; period/contact are runtime bindings | Router/service read records and last route | Yes: records and trace |
| Batch: propose/validate plan | `model_call`, accepted/rejected `plan`; active graph in memory | Planner sees its response and repair feedback | Validator/scheduler read active graph | Trace yes; active graph not restored |

### The critique loop (owner: claudea)

**Where it helps: `draft_report_email`.** Slide 43's three gates hold. *A check without solving the task:*
the recipient, quarter and revenue are each a lookup or one SQL sum (`sales.distributor_sales`). *The critic
knows what the author did not:* it reads the stored contact and quarter (not the stranger's claim) and
recomputes revenue from `orders`. The planner never sees the contact address (it writes `$fill`), so a
drafting model can invent one. The baseline shows it: in all three `batch_reports_two` runs
(`results/baseline/baseline-batch_reports_two-s0{1,2,3}-*.trace.jsonl`) the critique returned **6 drafts**
addressed to a literal `$fill:request.contact_email`, `{$fill:request.contact_email}` or `client@example.com`;
all 6 were revised, passed, and their runs passed their checks. *A limit and a log:* two rounds, each a
`critique` event.

**The check** (`agent/critique.py`, `check(request_id, draft)`), a pass or fail with a reason from the
sandbox alone, never a task's check: the recipient is the request's `contact_email`; `figures.period` is the
request's; `figures.total_revenue` (and the previous quarter's, if given) matches the database within 0.01;
the body states the total and no other revenue, period or direction; it names no other distributor and no
margins. These are bounded rules, not full understanding; the operator still reads the draft. **Bound:**
`rounds=2` (`CRITIQUE_ROUNDS`, `agent/workflows.py`): check, one revision with the reason, check again. Each
round logs its verdict (`pass`, `revise`, `held`), reason and changed fields. A draft still failing is
**held**: no pending record, the run ends `critique_held`, the operator is told. Switch
`critique.report_email`: `off | external`. **Paths:** the `standard_report` workflow and both agent paths
(through `EmailGate`) call the same `critique.run`. **Tests** (`tests/test_workflows.py`, fake models): a
failing draft is revised with its reason, is never written at the bound, and a passing draft is written once.

**Where it does not help: the `out_of_scope` decline** (fixed template, `agent/domain_workflows.py`). Code
writes every word and fills its one fact from the request record, so a check would read the same record the
template did: the critic knows nothing new (second gate fails). A model-written clarifying question has no
critique either: no record can say whether it is the right question (first gate fails); the operator reads it.

**Assignment 2's result** (Myron's [agentic-ai-assignment2](https://github.com/MyronLiu999/agentic-ai-assignment2),
commit `df425cc`, `reports/LAB_02.json`, `gpt-4.1-mini`, 18 runs per configuration, read 2026-10-31). With two
rounds, self and external critique averaged 0.22 and 0.17 rounds per run and changed no draft, while success
fell from 5/18 (off) to 3/18 and 2/18: its check tested facts the author already had right. It predicts a
critique pays only where the author can be wrong about a fact the critic sees. Our baseline differs on exactly
that: 6 drafts changed in 18 runs (21 rounds, 1.17 per run), none held. One miss remains
(`baseline-messy_file_semicolon-s01-1799cc`): the critic does not check the file's unit total.
[Source and test detail](M1-evidence.md).

### Write identity and environmental confirmation

The registry generates `tool:v1:sha256(canonical_json)` from version, run ID
(or console session), request ID, tool name and either a code-owned logical
step or effect fields. JSON keys are sorted with fixed separators. Reactive
model rounds use `trace_step` only for attribution; they do not change write
identity. Without a fixed step, chart identity is the ordered series labels and numeric values,
excluding its display title; equivalent integral JSON numbers such as `10` and `10.0`
have the same identity. Changed data/category series get a distinct chart. Report identity is
kind/figures.period, email identity is recipient/report ID, and clarification
identity is the bound request/tool. Prose is excluded. Thus a same-effect retry
returns the first artifact/row; a genuinely revised report needs a new logical
step/key, not reworded prose. Sandbox reports/pending/charts enforce the key.

**Where the key is checked** (slides 38 and 39). `reports`, `pending` and `charts` each have a
`key ... UNIQUE` column (`sandbox/db.py`); each `add`/`save` reads for the key first and returns the first row
to a repeat. Between that read and the write, another writer with the same key (a second console session
replaying the call) could insert; the `UNIQUE` constraint then rejects the second insert, so the effect stays
single. The outside channel takes no key, but the agent never sends on it; the operator's send first claims
the record (`pending` → `sending`) in one conditional `UPDATE`, so a double click sends once.

| Write | Environment read that confirms it | If it cannot answer; escalation |
|---|---|---|
| Chart | `charts.get(chart_id)` plus SVG file read | Halt/hold; analyst inspects row and artifact before retry |
| Report | `reports.for_request(request_id)` matching returned report ID/key/figures | Hold; analyst inspects DB, never infer success from model prose |
| Pending email | `pending.get(pending_id)` matching request, report, contact and key | Hold; analyst checks pending records before sending |
| Pending question | `pending.get(pending_id)` matching request/contact/kind/key | Hold; analyst checks pending state before retry |

The trace now preserves the complete caller result, including error details;
only `result_summary` is shortened. Every call keeps latency, key, attempts,
outcome and zero local tool cost. `tests/test_registry.py` covers long results
and full errors; `tests/test_analysis_boundary.py` verifies classification of
current and legacy records. This does not add Milestone 2 crash-resume behavior.
