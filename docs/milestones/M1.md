## Part 1: The first version

Owners: Claudea (domain/workflows/actions), Abraham (routing/gates).

The user is a sales analyst receiving distributors' uploads and quarterly questions. The core task decodes a file, queries that distributor's authoritative sales, saves a chart/report, and prepares an email for operator review. Unknown meaning produces a pending question and stops; outside-answer resumption belongs to Milestone 2. All identities/data are synthetic. The six official tasks represent one working day's clean report, unfamiliar export, comparison, status, restricted request and batch; the monthly-column development file is separate.

Success is an independently checked sandbox effect, not a “done” reply: correct named report fields, correct request/period/contact/report link, exactly one active pending email and no detected foreign/private data. Messy-file units and comparison revenue have required named fields; unrelated true numbers cannot substitute. Finite-number and contextual-prose regressions challenge these checks. Literal leak checks and the deterministic prose parser are bounded detectors, not a guarantee about arbitrary language.

Untrusted text lives in distributor messages/files; margins and other distributors' orders are private; operator-sent email is the way out. Tools bind distributor/contact from trusted request records and cannot read margins. Pending drafts are private records, not publication. Code resolves request scope and obvious intent; one bounded model classification handles ambiguous work/status intent without outside file contents. Status follow-ups recover selected IDs from the session trace. Ambiguous names, exclusions or selections ask for clarification. The standard workflow fixes parse/query/chart/save/email order; status reads records; out-of-scope uses a fixed decline.

Borrowing A1 provisionally gives `c=$0.000595960`, `m=3.34194`, extra cost `c(m−1)=$0.001395700`. A1's measured benefit fraction is `f=0/6`; the sales estimate `f=0.10` is explicitly unmeasured. Assume fifteen minutes' correction labor at $42.76/hour: `W=$10.69`, using the [BLS wage proxy](https://www.bls.gov/ooh/math/operations-research-analysts.htm), read 2026-10-31. Neither occupation proxy nor correction duration is project evidence. Unfamiliar-file cost per extra correct case is `c(m−1)/f=$0.013957`; break-even `f*=c(m−1)/W=0.00013056`. At `f=0.0001`, cost rises to $13.957 and the verdict reverses. Clean reports assume `f=0`, giving no finite benefit ratio. Wrong-case losses must also count.

Routing share `r` differs from benefit `f`: illustrative `r=0.10` gives blended `c[(1−r)+rm]=$0.000735530`, versus workflow-only $0.000595960 and all-agent $0.001991660. These estimates exclude routing overhead. Project-local paired cost/success, correction time and observed adaptive steps must validate or reverse them; the measured examples pass does not estimate agent/workflow `m` or `f`. Extended arithmetic and sensitivity are in the [technical notes](M1-evidence.md#part-1-the-first-version-owners-claudea-the-gates-and-routing-abraham).

The economic verdict is sensitive to the human task being valued. At one minute of correction labor, `W=$0.71267` and break-even rises to `0.19584%`; at one hour, `W=$42.76` and it falls to `0.003264%`. These are scenarios using the same wage proxy, not observed repair times. The small project sample cannot establish benefit at such thresholds. For interaction, the handout's roughly ten-second threshold also matters: a cheaper agent that makes an analyst wait without progress may be the worse route. The service exposes action progress; Part 4 identifies slow turns rather than inferring acceptable latency from A1.

### Action grid and approval line (Claudea; tool contracts Myron)

The unified action/tool table in Part 3 states both undo and knowledge axes (L1 37,39). Ranked order is reads → correctable local artifacts/reports → discardable pending drafts → **operator approval line** → irreversible send. `charts.render`/`reports.save` supersede artifacts; `pending.discard` removes an unsent action from use. These are existing fix-ups, not deletion of history. Existence readback never proves all semantic claims. Unknown interpretation/chart meaning needs monitoring or review before use; local drafting is the automation limit. No send is an agent tool, even for a fixed decline. Atomic claims prevent two deliveries of the same pending row; ambiguous failures remain visible and cannot automatically retry. A completed older send cannot hide newer work. The trifecta is constrained by scoped access and this send boundary; literal leak filters do not prove paraphrased disclosures impossible.

### Plan and step size (Abraham)

Planning is on for the implemented batch agent because deliverables can be declared and missing steps checked (L2 5,54); the reactive unfamiliar-file investigation instead consumes observations (L2 17). This is a decision about controlling the chosen prototype, not evidence that homogeneous batches require an agent. Standard/status/decline workflows already enforce their sequence. Planning should be removed or replaced by workflow iteration if its prevented mistakes do not justify cost.

The planner receives only the operator instruction, tool contracts and allowlisted record IDs/counts. Stranger questions, files, addresses and periods are excluded. Code fills `request.period`/`request.contact_email` at execution. Replanning sees statuses/counts/integer IDs, not raw outputs/errors. Each step declares scope, arguments, earlier dependencies and an observable predicate. Validation rejects forward references, cross-request bindings, orphan work and missing terminal deliverables; execution follows listed order. Only a failed read checkpoint permits suffix revision. Completed positions/effects remain immutable; uncertain writes stop for inspection. A pending question stops the batch with a waiting thread.

| Unit of work | What advances it | Bound and reason |
|---|---|---|
| Reactive loop step | One model invocation, including incomplete-response retries and email revisions | 12 calls: provisional allowance for tool rounds, final response, revisions, and repairs |
| Planned execution step | One validated tool call with an observable outcome | At most 48 steps for up to eight requests; completed steps cannot be changed |
| Planning/replanning step | One complete JSON proposal | Initial proposal plus two replacements total; invalid plans consume the same allowance |
| Email revision | One tool-free model call proposing recipient, subject, body; planned contact remains code-bound | Passed to `critique.run(..., rounds=2)`; shares the execution budget; report and saved figures stay fixed |
| Execution token/time budget | Metered tokens since loop/batch entry and monotonic elapsed time | 150,000 tokens and 90 seconds, also constrained by the session ceiling; provisional interactive limits |

These cooperative bounds are traced and checked around calls; an in-flight synchronous operation can overshoot. The optional router classification precedes the execution allowance. Both paths emit exact-repeat diagnostics; plan diffs log executed/skipped/extra/out-of-order work. A recovered rejected proposal is not a terminal rejection. Tests cover valid order, invalid plans before effects, bounded failure, checkpoint repair and no replay of completed writes.

### Critique (Claudea)

The shared report-email gate resolves the actual saved report, pins its figures/comparison requirement, and independently recomputes contact/period/revenue from trusted records. Planned contacts are normalized before validation and remain fixed through revisions. The author may already have seen these facts; the useful distinction is independent verification, not privileged information. Supported email/report revenue assertions, supplied file units and comparison fields are checked; arbitrary prose remains outside this deterministic verifier's guarantee.

With `critique.report_email=external`, two logged checks allow one tool-free revision. A held draft creates no pending email; already saved reports/charts remain. Workflow, reactive and planned paths use the gate. A revised planned email is logged before execution. Fake-model tests demonstrate correction, bounded hold and effects; Part 4 reports real held drafts/misses. The decision table separately explains why fixed declines and model-written clarifying questions have no critique. Questions have scope/shape checks and operator review, not an oracle for unresolved meaning. Add critique only when a runtime source can detect that specific error without doing the unresolved task (L2 43).

## Part 3: The tools

Owner: Myron (contracts/treatments/measurements), Claudea (action risks).

Six request-bound tools form one sales/report domain; the registry validates authorization, arguments/results, bounded retries and write keys. Private-margin access and actual send are absent. T/P/A mean transient/permanent/ambiguous. Known locked-store errors retry at most twice; permanent errors return repair facts. An uncertain write stops for environment inspection.
