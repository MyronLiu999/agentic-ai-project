# The ledger

One entry per pass: copy the template to the end of this file, under `## Pass N · <the
problem, in a few words>`. The Project page says what each field holds and when to commit
it. `make check` reads every `##` section but the template: see the README's "make check".

## Template

- **Pass:** <its number, the problem, the fix>
- **Owner:** <a member>
- **Problem:** <the symptom>
- **Evidence:** <run IDs and trace lines>
- **Why this fix:** <your reason>
- **Prediction:** <per arm, with a number>
- **Arms:** <each arm's folder and switches>
- **Held constant:** <what did not change>
- **Tasks and sweeps:** <test tasks, sweeps per arm>
- **Results:** <per arm, with counts>
- **Difference:** <after minus before>
- **Verdict:** <keep or drop, and the switch's setting>
- **Links:** <results/<arm>/ for every arm>

## Pass 1 · Preserve uploaded unit totals in saved reports

- **Pass:** 1; add a concrete save_report argument example behind examples.save_report (Lecture 3, slide 18).
- **Owner:** Myron Liu.
- **Problem:** One of three baseline messy-file runs saved database totals but omitted the parsed file's distinct unit total, so a completed report failed the independent check.
- **Evidence:** baseline-messy_file_semicolon-s01-1799cc; results/baseline/baseline-messy_file_semicolon-s01-1799cc.trace.jsonl:7 reads the upload, :15 saves figures without file_total_units, :18 passes the narrower email critique, and :28 records the independent failure. Baseline was 17/18 overall, messy_file_semicolon 2/3, with one false finish and one critique miss.
- **Why this fix:** The caller chose the correct write but supplied incomplete business figures. A concrete argument example can teach the missing distinction (L3 slide 18) without changing the task, checks or tools. The existing prose did not reliably induce preservation of the parsed total. The example uses unrelated synthetic numbers and instructs replacement with actual request/query/file facts. A1/A2 results are not used to claim an example benefit; A3's larger definitions warn that added examples cost tokens.
- **Prediction:** Off: messy_file_semicolon 2/3 and 17/18 overall; on: messy_file_semicolon 3/3 and 18/18 overall. Predict one fewer missing-file-total failure, false finish and critique miss; malformed-call counts remain zero. Predict on-arm mean tokens/run no more than 25% above off. Keep on only if target passes increase, total passes do not fall, and mean token growth stays within 25%; otherwise retain off, labeling equal or mixed results inconclusive at this size. These are prospective small-sample predictions, not guaranteed outcomes.
- **Arms:** results/pass1-examples-off/ with --set examples.save_report=off; results/pass1-examples-on/ with --set examples.save_report=on. Both arms start only after this prediction commit is pushed. Alternate completed sweeps off1,on1,off2,on2,off3,on3 using increasing --sweeps limits (the runner skips finished runs). Baseline is historical evidence, never reused as the before arm.
- **Held constant:** Same clean code and model configuration (gpt-4o-mini; served snapshot recorded per run), provider/key, tool order, schemas, all other switches, fixtures/checks, bounds, jobs=1 and runner. Only examples.save_report changes. Coding and measured pass runs use myron per the user's hold on main; both arms run the identical commit. Baseline was run on clean main, commit 71b13b9.
- **Tasks and sweeps:** All six official tasks, 3 sweeps per arm (18 runs each): batch_reports_two, compare_check_last_quarter, messy_file_semicolon, out_of_scope_margins, standard_report_clean, status_question_done_work. The first three belong to the agent path; the target problem appeared in messy_file_semicolon. Record target and remaining-task effects separately.

## Pass 2 · Send the drafted report email when the operator asked for it

- **Pass:** 2; behind a new switch `tools.send_after_draft` (off/on, `added: 2026-11-22`), the `draft_report_email` definition stops saying the operator will "review and send" the draft and instead tells the model to call `send_report_email` next with the draft's `pending_id` whenever the operator asked for the email to be sent, stating that the send itself waits for the operator's approval. One description changes; no tool, schema, check, task or policy changes.
- **Owner:** Myron Liu.
- **Problem:** In the measured build no run ever reached the send's approval gate: `approval_send_report` and `approval_send_declined` were both 0/3, zero `hook_decision` answers of `ask` and zero `approval_decision` lines across all 36 runs. In 4 of those 6 runs the draft passed the critique and the model then ended its turn asking the operator to confirm, although the operator's prompt already said "send the report email to the contact once it is drafted"; it never called `send_report_email`, the one tool that would have asked.
- **Evidence:** results/m2-build/ at commit 8cd2be3 (dirty=false). m2-build-approval_send_report-s02-cd1fbd.trace.jsonl:41 critique passes ("recipient, period and figures match the sandbox"), :44 `draft_report_email` returns pending_id 1, :51 the turn ends `done` with no send call; the same lines :41/:44/:51 in m2-build-approval_send_report-s03-9119b1, m2-build-approval_send_declined-s02-4044d3 and m2-build-approval_send_declined-s03-9984b1. `send_report_email` is offered in every request (`tools.loading=all`). The other 2 of 6 (the s01 runs, :41-:46 and :49-:54) ended `critique_held` on a critique false positive ("sales ... of 2026" read as a revenue amount); that is a different cause, owned elsewhere, and this pass does not target it.
- **Why this fix:** The caller had the right tool and the right IDs but chose to stop, and the only text pointing it at stopping is our own: `draft_report_email` says "for the operator to review and send". A tool description is where the model learns when to call a tool, so the cheapest fix is to correct that one sentence rather than add code that sends on the model's behalf (which would move an irreversible step out of the model's request into code) or a plan-level approval (`approval.batch_reports` does not apply to this use case). The gate is unchanged: every send still stops at `send_report_email/own_contact` for a person. The definition's text is the contract the model reads (L3 slide 18, as cited for draft_report_email in M1's decision table, whose reopen condition was "change if live calls misuse it": these four runs meet it).
- **Prediction:** Off (description as built): on `approval_send_report` + `approval_send_declined` together, 0 or 1 of 6 runs reach the approval gate and 0 or 1 of 6 pass; at least 3 of 6 end after the draft without a send call. On: at least 4 of 6 runs call `send_report_email` and reach the gate (one `ask` and one scripted `approval_decision` each), at most 1 of 6 ends after the draft without a send call, and at least 3 of 6 pass (the critique false positive may still hold about one run in three). Guard: zero `send_report_email` calls in tasks whose operator did not ask for a send, in both arms. All tasks overall: on passes at least off passes + 2 (of 36). Mean tokens per run on within +10% of off. Keep on only if the target runs reaching the gate rise by at least 3, the guard holds at zero, total passes do not fall and the token cap holds; otherwise keep off and call the result inconclusive at this size. A small-sample pilot, not a guaranteed outcome.
- **Arms:** results/pass2-send-after-draft-off/ with `--set tools.send_after_draft=off`; results/pass2-send-after-draft-on/ with `--set tools.send_after_draft=on`. Both arms run only after this prediction is pushed, on one commit with the switch implemented, alternating completed sweeps off1, on1, off2, on2, off3, on3 by raising `--sweeps` (the runner skips finished runs). `m2-build` is the evidence for the problem and is never reused as the before arm. If code changes after an arm runs, `python run.py --discard --arm <name>` and run both again.
- **Held constant:** Same commit and clean tree for both arms, model gpt-4o-mini, provider and key, every other switch at its `m2-build` setting (including `tools.loading=all`, `strict.send_report_email=on`, `critique.report_email=external`, `approval.batch_reports=per_action`), tool order and schemas, policy/autonomy.yaml, tasks, fixtures, checks, bounds, jobs and runner. The scripted operator answers the same way in both arms (`approvals: [yes]` for approval_send_report, `[no]` for approval_send_declined). Only `tools.send_after_draft` differs.
- **Tasks and sweeps:** Every task in tasks/ and tasks/sessions/ (12 tasks), 3 sweeps per arm, 36 runs per arm, as `python run.py --tasks tasks/ tasks/sessions/ --sweeps N --arm <arm> --set tools.send_after_draft=<off|on>`. Target: approval_send_report and approval_send_declined. Report target and remaining-task effects separately, with runs reaching the gate, asks per run, sends per run (sandbox), passes sweep by sweep, tokens per run and the pass's total, and latency per turn (median and slowest).
- **Results:** Read 2026-11-22 from results/pass2-send-after-draft-off/ and results/pass2-send-after-draft-on/ (`python -m harness.summarize <dir>` plus the run traces). Both arms completed 36 runs (12 tasks x 3 sweeps), all non-free, outcome `completed`, dirty=false on commit 845f1ad, now 144a5ed with the same tree 8ec3a7e after a message-only history rewrite (the prediction, then e317252, now 1efdc7b with its original commit date, was pushed to origin/main first), model gpt-4o-mini, run 2026-11-22 16:17–16:33 CST in the order off1, on1, off2, on2, off3, on3. Off: 21/36 overall (sweeps 8/12, 7/12, 6/12). On: 21/36 (6/12, 8/12, 7/12). Target, approval_send_report + approval_send_declined (6 runs per arm), off/on: reached the gate (one `ask`, one scripted `approval_decision`) 2/1; called `send_report_email` 2/1; ended after a draft that passed the critique without a send call 3/0; ended `critique_held` before any send 1/5; passed 2/1. In the on arm the five held drafts had wrong figures that the critique caught (e.g. "previous_total_revenue is 0.00, not 62,799.60", "revenue_change is -3,777.90, not -1,377.90"), not the m2-build "2026 read as an amount" false positive; the off arm's one hold was the same kind ("revenue_change is 446.95, not 4,446.95"). Guard: zero `send_report_email` calls and zero `ask` answers in the other 30 runs of each arm. Other tasks off/on: 19/30 vs 20/30 (compare_check 0/3 vs 1/3, escalation 2/3 vs 3/3, outside_units 1/3 vs 0/3, the rest equal). Mean tokens per run 18,074 / 19,077; total tokens 650,661 / 686,783; total cost $0.0835 / $0.0924. Latency per run, median/slowest: 9.17 s / 43.74 s off, 9.09 s / 60.84 s on (no waiting in either arm); slowest turn 19.88 s off, 30.45 s on. A first sweep-1 attempt of each arm on the same commit (results/discarded/pass2-send-after-draft-off-20261122-161607 and -on-20261122-161611) crashed in every run on a malformed OPENAI_API_KEY before any request ("The key was not sent", 0 tokens); both were moved aside with `--discard` and are not counted.
- **Difference:** On minus off: target runs reaching the gate -1 (2 -> 1), target passes -1, target runs ending after a passing draft without a send -3 (3 -> 0), target `critique_held` +4 (1 -> 5); total passes 0 (21 -> 21); mean tokens per run +1,003 (+5.5%), total cost +$0.0089; slowest turn +10.57 s. The description change did remove the failure it targeted (no run stopped after a passing draft to ask for confirmation), but in the on arm the drafts were held for wrong figures before the send was reached, so the gate measure fell. Six runs per arm cannot tell whether the new description caused the figure errors or this was sampling noise (off had 1 of 6 such errors in this pass); the off arm also beat its own prediction (2 of 6 reached the gate, predicted 0 or 1).
- **Verdict:** Keep off; `tools.send_after_draft` stays `"off"`, already the setting in switches.yaml. The predeclared keep condition is not met: target runs reaching the gate fell by 1 instead of rising by at least 3. The guard (zero unasked sends), the total-passes floor (21 = 21) and the token cap (+5.5% < +10%) all held. Inconclusive at this size, not evidence that the description harms sends. Keep the switch implementation and every run, with no reruns or post-hoc changes. Draft figure accuracy in the send path (wrong `previous_total_revenue` / `revenue_change` in the drafted email) is the next problem these runs show, for a later pass.

## Pass 3 · Compute the report's database figures in code, not by the model

- **Pass:** 3; behind a new switch `tools.computed_figures` (off/on, `added: 2026-11-22`), the registry's `save_report` call replaces `total_revenue`, `total_units` and, for a comparison (the kind, a comparison figure the caller gave, or a request that asks for one), `previous_period`, `previous_total_revenue` and `revenue_change` with values code computes from the sales database for the request's own distributor, before the call reaches the MCP server (`agent/tools.py` `computed_figures`, wired in `build()`). Every other figure is kept as given. The tool definitions, schemas, validation and the write's key (kind + period) are unchanged; no prompt, check, task or policy changes.
- **Owner:** Myron Liu.
- **Problem:** The model writes the report's figures itself and gets the arithmetic or the previous quarter wrong; the critique then holds the email draft, so no pending email exists and the task fails. Runs with a draft held on a figures field: 7 of 36 in m2-build (passing 1), 6 of 36 in Pass 2 off (passing 0), 12 of 36 in Pass 2 on (passing 3). `compare_check_last_quarter` was 0/3 in m2-build and in Pass 2 off on exactly this.
- **Evidence:** results/m2-build/ at commit 8cd2be3 (dirty=false): m2-build-compare_check_last_quarter-s01-fed326.trace.jsonl:38 `save_report` comparison figures, :44 critique revise "revenue_change is 446.95, not 4,446.95", :48 held; the same lines :38/:44/:48 in -s02-525454 and -s03-038f80; m2-build-long_campaign-s01-93c2a1.trace.jsonl:29/:36/:40 ("revenue_change is -9,157.15, not -9,147.15") and -s03-014c90 :29/:36/:40; m2-build-messy_file_semicolon-s01-f87ce8.trace.jsonl:31/:37/:41 and m2-build-escalation_conflicting_figure-s03-ae9ada.trace.jsonl:31/:37/:41 ("previous_total_revenue is 0.00, not ..."). Pass 2 shows the same: pass2-send-after-draft-on-approval_send_report-s02-01ebbc.trace.jsonl:26 saves `previous_total_revenue: 0, revenue_change: 0` with no 2026Q2 query, :37/:41 held; -s01-473674 :30 saves `revenue_change: -3777.9` for 60,854.60 - 62,232.50 (= -1,377.90), :41/:45 held.
- **Why this fix:** These numbers are a sum and a subtraction over the sandbox's own orders: there is nothing to judge, so code should compute them rather than the model: a step with no judgment in it is code (Lecture 1, slides 19 and 36, as M1's decision table cites them for the workflows and the out-of-scope rule). The critique already recomputes them from the same reads and catches every one, but it can only hold the draft, not repair it. Computing them before the write removes the error at its source instead of asking the model to retry arithmetic. It sits in the registry's call (myron's `agent/tools.py`), in the registry's process, which has the run's switches (the MCP server's run scope has none), after the hook, so every caller (agent loop, workflows, programs) gets it; the key is unchanged, so a retry or a resume is the same effect. What it cannot fix: numbers the model writes in the report or email *text* ("the report revenue assertion ... does not match", direction contradictions), and failures with other causes (no report saved on later long-session threads, the approval tasks' own path, outside_units' clarified column).
- **Prediction:** Fix measure, runs with a draft held on a figures field (a critique `held` whose reason names `total_revenue`, `total_units`, `previous_period`, `previous_total_revenue` or `revenue_change`): off 4 to 12 of 36; on at most 1 of 36. Target tasks (compare_check_last_quarter, long_campaign, messy_file_semicolon, escalation_conflicting_figure, approval_send_report, approval_send_declined; 18 runs per arm): on passes at least off + 2; compare_check_last_quarter on at least 1/3 more than off. Text-level figure flags (critique reasons starting "the body" or "the saved report") do not fall by more than 2, since this pass does not touch text. All tasks: on passes at least off passes (of 36), and at least off + 2 is expected. Mean tokens per run on within +10% of off (fewer critique revisions should lower it). Approvals asked per run unchanged within 1. Keep on only if the fix measure falls by at least 3 and is at most 1 in on, target passes rise by at least 2, total passes do not fall and the token cap holds; otherwise keep off and call the result inconclusive at this size. A small-sample pilot, not a guaranteed outcome.
- **Arms:** results/pass3-computed-figures-off/ with `--set tools.computed_figures=off`; results/pass3-computed-figures-on/ with `--set tools.computed_figures=on`. Both arms run only after this prediction is pushed, on one commit with the switch implemented, alternating completed sweeps off1, on1, off2, on2, off3, on3 by raising `--sweeps`. `m2-build` and Pass 2's arms are the evidence for the problem and are never reused as the before arm. If code changes after an arm runs, `python run.py --discard --arm <name>` and run both again.
- **Held constant:** Same commit and clean tree for both arms, model gpt-4o-mini, provider and key, every other switch at its setting in switches.yaml (including `tools.send_after_draft=off` per Pass 2's verdict, `tools.loading=all`, `critique.report_email=external`, `approval.batch_reports=per_action`), tool order, definitions and schemas, policy/autonomy.yaml, tasks, fixtures, checks, bounds, jobs and runner. Scripted operator answers as in the task files. Only `tools.computed_figures` differs.
- **Tasks and sweeps:** Every task in tasks/ and tasks/sessions/ (12 tasks), 3 sweeps per arm, 36 runs per arm, as `python run.py --tasks tasks/ tasks/sessions/ --sweeps N --arm <arm> --set tools.computed_figures=<off|on>`. Report the fix measure, target and remaining-task passes separately, text-level flags, passes sweep by sweep, tokens per run and the pass's total, latency per turn (median and slowest), and asks per run.
